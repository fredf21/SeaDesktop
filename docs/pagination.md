# SeaDesktop — Pagination

Reference documentation for pagination on CRUD routes generated by SeaDesktop. This document describes each supported YAML key, its allowed values, its default behavior, and the expected system behavior. All information comes from the project source code.

## 1. General principle

By default, the `GET /<entity>` route returns all records for an entity. For large tables, this behavior becomes inefficient. Pagination splits results across multiple requests.

SeaDesktop provides three independent pagination modes:

- **`page`**: pagination by page number and page size
- **`offset`**: pagination by offset and limit
- **`cursor`**: pagination by opaque cursor

The three modes can be enabled simultaneously on the same entity. Each mode then produces its own distinct route with its own response format.

The `GET /<entity>` route without a suffix always remains available and returns all records, regardless of which modes are enabled.

---

## 2. Enabling pagination

Pagination is enabled in an entity's `pagination:` block. At least one of the three sub-blocks (`page`, `offset`, `cursor`) must be present.

### General structure

```yaml
entities:
  - name: Product
    fields: [ ... ]
    pagination:
      page:    { ... }
      offset:  { ... }
      cursor:  { ... }
```

### Behavior when the block is absent

If the `pagination:` block is absent from an entity, no paginated route is generated. Only the standard `GET /<entity>` route is exposed.

### Behavior when `pagination:` is present but empty

If the `pagination:` key is declared without at least one of the three sub-blocks, service startup fails with the following error:

```text
[YAML PARSING EXCEPTION] 'pagination' of entity '<name>' must contain
at least one mode among 'page', 'offset' or 'cursor'.
```

---

## 3. Generated routes

For each enabled mode, a separate route is created:

| Enabled mode | Generated route |
|---|---|
| `page` | `GET /<entity>/page` |
| `offset` | `GET /<entity>/offset` |
| `cursor` | `GET /<entity>/cursor` |

The `<entity>` segment corresponds to the entity name in lowercase plural form. For example, a `Product` entity produces `/products/page`, `/products/offset`, and `/products/cursor`.

The `GET /<entity>` route remains accessible and returns all records. Paginated routes are additional routes, never replacements.

---

## 4. `page` mode

The `page` mode provides classic pagination with page numbers and page size. It is suitable for interfaces displaying navigation links between pages.

### Configuration

```yaml
pagination:
  page:
    default_page_size: 20
    max_page_size: 100
    default_sort: "created_at:desc"
    sortable_fields:
      - created_at
      - name
      - price
```

### Accepted keys

| Key | Type | Default value | Description |
|---|---|---|---|
| `default_page_size` | integer | `20` | Page size applied if the client does not provide one in the request. |
| `max_page_size` | integer | `100` | Maximum allowed page size. A larger client value is capped at this limit. |
| `default_sort` | string | absent | Default sorting. Format: `"<field>:<direction>"`, where direction is `asc` or `desc`. |
| `sortable_fields` | list of strings | `[]` | Whitelist of fields allowed for sorting. See [section 8](#8-sortable-fields-whitelist). |

### Route and parameters

```text
GET /<entity>/page
```

| Query parameter | Type | Description |
|---|---|---|
| `page` | integer | Page number. The index starts at 1. |
| `page_size` | integer | Page size. Capped at `max_page_size`. |
| `sort` | string | Sorting to apply. Format: `"<field>:<direction>"`. |

### Response format

```json
{
  "items": [
    { "id": "...", "name": "...", ... }
  ],
  "page": 2,
  "page_size": 20,
  "total": 532,
  "total_pages": 27,
  "sort": "created_at:desc"
}
```

| Key | Description |
|---|---|
| `items` | Records for the requested page. |
| `page` | Current page number. |
| `page_size` | Effective page size after possible capping. |
| `total` | Total number of records in the table. |
| `total_pages` | Total number of available pages. |
| `sort` | Applied sorting. |

### Example

```bash
curl "http://localhost:8081/products/page?page=2&page_size=20&sort=name:asc"
```

### Expected behavior

1. Validate parameters: `page` ≥ 1, `page_size` ≥ 1.
2. If `page_size` is absent, `default_page_size` is used.
3. If `page_size` exceeds `max_page_size`, the value is silently capped.
4. If `sort` is absent and `default_sort` is defined, default sorting is applied.
5. If `sort` is provided, its field must belong to `sortable_fields`; otherwise, a 400 status code is returned.
6. A `SELECT COUNT(*)` query is executed to calculate `total`.
7. A `SELECT ... ORDER BY ... LIMIT page_size OFFSET ((page-1) * page_size)` query returns the records.

## 5. `offset` mode

The `offset` mode provides pagination by arbitrary offset. It is the closest mode to standard SQL and is suitable for administration tools and exports.

### Configuration

```yaml
pagination:
  offset:
    default_limit: 20
    max_limit: 100
    default_sort: "id:asc"
    sortable_fields:
      - id
      - name
      - created_at
```

### Accepted keys

| Key | Type | Default value | Description |
|---|---|---|---|
| `default_limit` | integer | `20` | Limit applied if the client does not provide one. |
| `max_limit` | integer | `100` | Maximum allowed limit. |
| `default_sort` | string | absent | Default sorting. |
| `sortable_fields` | list of strings | `[]` | Whitelist of sortable fields. |

### Route and parameters

```text
GET /<entity>/offset
```

| Query parameter | Type | Description |
|---|---|---|
| `offset` | integer | Number of records to skip before starting. |
| `limit` | integer | Maximum number of records to return. |
| `sort` | string | Sorting to apply. |

### Response format

```json
{
  "items": [
    { "id": "...", "name": "...", ... }
  ],
  "offset": 40,
  "limit": 20,
  "total": 532,
  "sort": "created_at:desc"
}
```

### Example

```bash
curl "http://localhost:8081/products/offset?offset=40&limit=20&sort=created_at:desc"
```

### Expected behavior

1. Validate parameters: `offset` ≥ 0, `limit` ≥ 1.
2. If `limit` is absent, `default_limit` is used.
3. If `limit` exceeds `max_limit`, the value is silently capped.
4. If `offset` is absent, `0` is used.
5. SQL query: `SELECT ... ORDER BY <sort> LIMIT <limit> OFFSET <offset>`.

---

## 6. `cursor` mode

The `cursor` mode provides pagination by opaque cursor. Performance remains constant regardless of pagination depth. This mode is suitable for real-time lists, infinite scrolling, and mobile applications.

### Configuration

```yaml
pagination:
  cursor:
    default_limit: 20
    max_limit: 100
    cursor_field: id
    sort: "id:asc"
```

### Accepted keys

| Key | Type | Required | Default value | Description |
|---|---|---|---|---|
| `default_limit` | integer | No | `20` | Limit applied if the client does not provide one. |
| `max_limit` | integer | No | `100` | Maximum allowed limit. |
| `cursor_field` | string | **Yes** | — | Field used as cursor. It must be unique and stably sortable. |
| `sort` | string | **Yes** | — | Fixed cursor sorting. Format: `"<field>:<direction>"`. The field must match `cursor_field`. |

### Route and parameters

```text
GET /<entity>/cursor
```

| Query parameter | Type | Description |
|---|---|---|
| `after` | string | Opaque cursor returned by the previous request. If absent, the first page is returned. |
| `limit` | integer | Maximum number of records to return. |

Sorting is **not** configurable by the client: it is fixed by the `sort` value in the configuration. Any client-side `sort` parameter is ignored.

### Response format

```json
{
  "items": [
    { "id": "...", "name": "...", ... }
  ],
  "limit": 20,
  "next_cursor": "eyJpZCI6IjU1MGU4LS4uLiJ9",
  "prev_cursor": null
}
```

| Key | Description |
|---|---|
| `items` | Returned records. |
| `limit` | Effective limit. |
| `next_cursor` | Cursor to use to retrieve the next page. `null` if the end has been reached. |
| `prev_cursor` | Cursor for the previous page. `null` on the first page. |

### Example request sequence

**First page:**

```bash
curl "http://localhost:8081/products/cursor?limit=20"
```

Response:

```json
{
  "items": [ ... 20 products ... ],
  "limit": 20,
  "next_cursor": "eyJpZCI6IjU1MGU4LS4uLiJ9",
  "prev_cursor": null
}
```

**Next page:**

```bash
curl "http://localhost:8081/products/cursor?after=eyJpZCI6IjU1MGU4LS4uLiJ9&limit=20"
```

### Expected behavior

1. The cursor is an opaque string: the client must reuse it as-is without modification or interpretation.
2. If `after` is absent, the query starts from the beginning, according to `sort`.
3. The SQL query uses a condition such as `WHERE <cursor_field> > <decoded_value>`, or `<` depending on the sort direction.
4. Sorting is fixed: any client-side `sort` parameter is ignored.
5. `cursor_field` must be unique. Otherwise, the cursor can produce inconsistent results.

### Why sorting is fixed

With a cursor, sorting cannot be changed dynamically. If the client changed sorting in the middle of pagination, previously returned cursor values would become invalid because they encode a position within the current sort order. This is why `sort` is defined once in the configuration and is not configurable by the client.

## 7. Sorting results

The `page` and `offset` modes accept a client-side `sort` parameter. The `cursor` mode ignores this parameter.

### Format

Sorting follows the `"<field>:<direction>"` format:

| Example | Effect |
|---|---|
| `created_at:desc` | Sort by creation date in descending order. |
| `name:asc` | Sort by name in ascending order. |
| `price:desc` | Sort by price in descending order. |

### Default direction

If the direction is omitted (`sort=name`), the sort direction is ascending (`asc`).

### Combining sorts

The system accepts one sort field at a time. For multi-field sorting, use a composite default sort declared in `default_sort`.

---

## 8. Sortable fields whitelist

The `sortable_fields` field is a security measure against SQL injection and costly queries on non-indexed fields.

### Behavior

If a client sends `sort=<field>`:

| Case | Behavior |
|---|---|
| `<field>` belongs to `sortable_fields` | Sorting is applied. |
| `<field>` does not belong to `sortable_fields` | A 400 status code is returned with a message stating that the field is not sortable. |
| `sortable_fields` is empty and `default_sort` is absent | No sorting is possible. Any `sort` value is rejected. |

### Recommendation

For each paginated entity, explicitly declare the fields allowed for sorting. These fields should ideally be indexed in the database with `indexed: true` at field level to guarantee good performance.

```yaml
entities:
  - name: Order
    fields:
      - name: id
        type: uuid
      - name: created_at
        type: timestamp
        indexed: true
      - name: total
        type: decimal
        indexed: true
      - name: customer_name
        type: string

    pagination:
      page:
        default_page_size: 20
        max_page_size: 100
        default_sort: "created_at:desc"
        sortable_fields:
          - created_at
          - total
        # customer_name intentionally absent: no index, sorting too expensive
```

## 9. Combining the three modes

The three modes can coexist on the same entity. Each mode then produces its own route with its own response format.

### Example

```yaml
- name: Article
  pagination:
    page:
      default_page_size: 10
      max_page_size: 50
      default_sort: "published_at:desc"
      sortable_fields: [published_at, title]
    offset:
      default_limit: 10
      max_limit: 100
      default_sort: "id:asc"
      sortable_fields: [id, published_at]
    cursor:
      default_limit: 20
      max_limit: 100
      cursor_field: id
      sort: "id:asc"
```

Routes exposed simultaneously:

| Route | Mode |
|---|---|
| `GET /articles` | No pagination, returns everything. |
| `GET /articles/page` | Page-based pagination. |
| `GET /articles/offset` | Offset-based pagination. |
| `GET /articles/cursor` | Cursor-based pagination. |

The client chooses the mode that fits its use case.

## 10. Error behavior

### Parameter validation

| Error | Returned code | Cause |
|---|---|---|
| `page < 1` | 400 | Invalid page number. |
| `page_size < 1` or `limit < 1` | 400 | Invalid page size. |
| `offset < 0` | 400 | Invalid offset. |
| `sort=field` with a field not listed in `sortable_fields` | 400 | Field not allowed for sorting. |
| `sort` with an unknown direction other than `asc` or `desc` | 400 | Invalid direction. |
| `after=<invalid cursor>` | 400 | Opaque cursor cannot be read. |

### Automatic capping

`page_size` or `limit` values greater than `max_page_size` / `max_limit` are **capped without error**. The system silently applies the maximum value, and the `page_size` or `limit` field in the response reflects the effective value.

```bash
# Configuration: max_page_size = 100
# Request: page_size = 500
curl "http://localhost:8081/products/page?page_size=500"

# Response contains: "page_size": 100 (capped, no error)
```

### Error format

```json
{
  "error": "Validation failed",
  "details": {
    "sort": "field 'description' is not sortable"
  }
}
```

## 11. Comparison of the three modes

### Summary table

| Criterion | `page` | `offset` | `cursor` |
|---|---|---|---|
| Arbitrary navigation, for example jump to page 50 | ✓ | ✓ | ✗ |
| Constant performance at deep pagination levels | ✗ | ✗ | ✓ |
| Total counter available | ✓ | ✓ | ✗ |
| Dynamic client-side sorting | ✓ | ✓ | ✗ |
| Suitable for real-time feeds | ✗ | ✗ | ✓ |

### When to use `page`

- User interfaces displaying navigation links, such as page 1, 2, 3, and so on.
- Moderate volumes, under 100,000 records, where degradation remains acceptable.
- Cases where the total counter is useful to display “532 results”.

### When to use `offset`

- Administration tools that allow arbitrary jumps.
- Paginated exports where the client knows the offset from application state.
- Expected standard SQL behavior.

### When to use `cursor`

- Infinite mobile lists, scrolling downward.
- Real-time feeds where records are continuously added.
- Very large volumes, above 1 million records, where `page` / `offset` performance becomes prohibitive.

## 12. Configuration examples

### Configuration 1 — Product catalog with page-based pagination

```yaml
- name: Product
  fields:
    - name: id
      type: uuid
    - name: name
      type: string
      required: true
      max_length: 200
    - name: price
      type: decimal
    - name: created_at
      type: timestamp
      indexed: true

  pagination:
    page:
      default_page_size: 24
      max_page_size: 96
      default_sort: "created_at:desc"
      sortable_fields:
        - created_at
        - name
        - price
```

### Configuration 2 — Real-time feed with cursor

```yaml
- name: Event
  fields:
    - name: id
      type: uuid
    - name: occurred_at
      type: timestamp
      indexed: true
    - name: payload
      type: json

  pagination:
    cursor:
      default_limit: 50
      max_limit: 200
      cursor_field: id
      sort: "id:desc"
```

### Configuration 3 — All modes enabled

```yaml
- name: Order
  fields:
    - name: id
      type: uuid
    - name: customer_id
      type: uuid
      indexed: true
    - name: total
      type: decimal
    - name: created_at
      type: timestamp
      indexed: true

  pagination:
    page:
      default_page_size: 25
      max_page_size: 100
      default_sort: "created_at:desc"
      sortable_fields: [created_at, total]

    offset:
      default_limit: 50
      max_limit: 500
      default_sort: "id:asc"
      sortable_fields: [id, created_at, total]

    cursor:
      default_limit: 30
      max_limit: 100
      cursor_field: id
      sort: "id:desc"
```

### Configuration 4 — Minimal pagination

```yaml
- name: Comment
  fields:
    - name: id
      type: uuid
    - name: content
      type: text
    - name: created_at
      type: timestamp
      indexed: true

  pagination:
    page:
      default_sort: "created_at:desc"
      sortable_fields: [created_at]
```

The other keys, `default_page_size` and `max_page_size`, use their default values: `20` and `100`.
